## 1. Зачем это

В вашем полном прогоне политика TSR (маршрут Дейкстры один раз в источнике, без починки; пакет, у которого следующий узел маршрута недоступен, ждёт до истечения TTL) при N = 132 и p = 0 потеряла долю пакетов 0,1323 (по предварительному чтению итогов: 397 из 3000; сверьте со своим `summary.json`). В нашем коде TTL равен 300 **секундам** (`ttl_s: 300.0` в `configs/simulation_n132.json`), а в открытом коде симулятора авторов статьи срок жизни сообщения хранится в **минутах** (по предварительному чтению того кода; не проверялось здесь). Проба отвечает на узкий вопрос: **куда деваются эти пакеты TSR, если TTL не может истечь внутри окна наблюдения**: доставляются позже, всё ещё ждут в конце окна или терпят неудачу по другой причине.

## 8. Как читать результат P1 и P2 (три строки)

Все числа берутся из `summary.json`: группа по `x` (0,0 или 0,04) → `policies` → `TSR_source_dijkstra` → `pooled_packet_and_call`.

1. `failure_fraction` — доля пакетов, завершённых как «failed» (в коде написано: отказ по `ttl`, `retry_exhaustion`, `injection_buffer`, `hop_limit` и т. д.; в `summary.json` причина не разбивается, она в `result.json`). У P1 и P2 по коду причины `ttl` быть не может; доказательство в три шага (вывод из чтения кода; не проверялось запуском): (1) момент истечения пакета = тик создания + TTL в тиках, тик создания не меньше 0; (2) симулятор (`simulator.run`) обходит тики от 0 до `horizon_tick` включительно, поэтому при TTL в тиках больше `horizon_tick` (12000 > 9000 в P1, 24000 > 18000 в P2) момент истечения больше любого тика цикла; (3) значит ветка `ttl` (ждущий пакет, у которого момент истечения не больше текущего тика; в коде это куча сроков, `expiry heap`) никогда не выполняется, и пакет, который к концу окна ещё ждёт, остаётся `pending`.
2. `pending_fraction` — доля пакетов, которые к концу окна ещё не доставлены и не потеряны, то есть «ещё ждут» (в коде написано: «right-censored»). Это не потеря, это незавершённость. `nondelivery_fraction` = `failure_fraction` + `pending_fraction`; доля доставленных = `delivered` / `generated`.
3. `delivered_mean_delay_s` — средняя задержка **только доставленных** пакетов. При TTL 300 с она не может превысить 300 с; при P1/P2 доставленные пакеты могут идти дольше.

Как сопоставить с P0 (TSR, p = 0; чтение, не наблюдение):

| Что видно в P1 | Что это означает |
|---|---|
| `failure_fraction` около 0, `pending_fraction` около прежних 0,13 | доля ждущих пакетов около 0,13 (гипотеза; чтение кода, не наблюдение); отдельные пакеты с пакетами P0 не отождествляйте: сравнивайте доли |
| `pending_fraction` заметно больше 0,13 | возможно (гипотеза; чтение кода, не наблюдение): заблокированная голова очереди теперь не снимается по TTL (строгий FIFO), и за ней ждут другие пакеты; сравнивайте доли, а не отдельные пакеты |
| `failure_fraction` около 0, `pending_fraction` заметно меньше, `delivered_mean_delay_s` выросла | часть пакетов доставляется позже, когда связь вернулась |
| `failure_fraction` у TSR при p = 0 остаётся больше 0,01 | пакеты теряются по причине, отличной от TTL: смотрите `terminal_reason_counts` в `result.json` |
| у TBR всё то же, что в P0 | при p = 0: TTL у TBR ничего не меняет (TBR не терял пакеты по TTL уже в P0: `failure_fraction` 0,0, ждущих 0); при p = 0,04: то же только если в `result.json` ячеек TBR шага P0 нет причины `ttl` (см. `metrics.terminal_reason_counts`), иначе различие объясняется TTL (вывод из чтения; не проверялось запуском) |

Отдельно про P2: по коду (вывод из чтения) состояние P2 на 900-й секунде совпадает с P1, а P2 затем показывает, что произошло за следующие 900 с; доставленных в P2 не меньше, чем в P1, ждущих не больше. Раз `packets.json` P2 хранит момент завершения каждого пакета, один P2 в принципе содержит и данные P1 (но уже не в `summary.json`, а в таблице пакетов). P1 всё равно стоит запустить: он даёт ответ прямо в сводке и дешевле.

Ещё одна оговорка: при p = 0,04 часть потерь TSR, вероятно (гипотеза; проверьте `terminal_reason_counts`), идёт по причине `retry_exhaustion`; эта часть при смене TTL не обязана остаться в точности той же: очередь ждущих пакетов меняется, а значит и порядок передач.
