## 1. Назначение

CGR отвечает на вопрос «каков самый ранний способ довезти пакет до назначения по **расписанию** встреч спутников, и в какого соседа и **в какой момент** отправлять первый хоп». План контактов — заранее вычисленный по геометрии список интервалов, в которых пара спутников связана. Поиск — зависящий от времени алгоритм Дейкстра **с ожиданием** на каждом узле. Первый хоп может быть в будущем: в этом отличие CGR от остальных маршрутизаторов, которые отвечают только «сейчас».

## 2. Что читает на самом деле

`packet.location`, `packet.destination`, `packet.expiry_tick` (крайний срок), `packet.size_bytes`; `context.tick`, `context.cfg`; `self.plan`. **Не читает** `context.adjacency`, `ranges_km`, `permitted_neighbors`, `packet.visited`, `header`, `hops` (в коде написано, комментарии `ContactRouting`: очереди, текущая занятость и случайные отказы план «NOT forecast»). Допустимость соседа проверяет симулятор, и только если вылет назначен на текущий тик.

## 3. Алгоритм `ContactRouting.choose`

```
choose(packet, context):
  plan_queries += 1                                     # на каждый вызов, и при попадании в память
  key = (location, destination, expiry_tick, size_bytes)
  memo = _none_memo[id(packet)]                         # сбрасывается, если другой packet / cfg / plan
  known = memo.get(key)                                  # первый тик, когда ответ был None
  if known is not None and tick >= known: return None    # память отрицательных ответов (часть D2)
  route = plan.earliest_hop(location, destination, tick, expiry_tick, size_bytes, cfg)
  if route is None:
      if known is None or tick < known: memo[key] = tick
      return None
  return Decision(route.neighbor, route.departure_tick)  # первый хоп; вылет может быть позже тика
```

Положительные ответы **не** запоминаются: план спрашивается на каждом вызове, **кроме** запомненного `None` для того же `(location, destination, expiry_tick, size_bytes)` — такой `None` переиспользуется, когда тот же запрос повторяется на последующих тиках (пока `tick >=` записанного тика). Строка `stats()["replanning"]` («each route call») относится к остальным вызовам.

## 4. Поиск `ContactPlan.earliest_hop`

Входы: `source`, `destination`, `now_tick`, `deadline_tick`, `size_bytes`, `cfg`. Проверки: узлы в `[0, N)`, тики — неотрицательные целые, `cfg.orbit.n == N`, иначе `ValueError`. `deadline = min(deadline_tick, horizon_tick)`. Если `source == destination` или `now >= deadline` → `None`.

```
labels = [inf]*N; labels[source] = now; heap = [(now, source)]; first = {}
while heap:
    arrival, node = pop(heap)                            # меньше (arrival, номер узла)
    if arrival != labels[node]: continue                 # устаревшая запись
    if node == destination:
        neighbor, departure = first[node]
        return PlannedHop(neighbor, departure, arrival)  # arrival — прибытие в НАЗНАЧЕНИЕ
    for nb in neighbors[node]:                           # по возрастанию; все пары, бывшие смежными хоть раз в горизонте
        r = _edge_arrival(node, nb, arrival, deadline, size, cfg, limit = labels[nb])
        if r is None: continue
        next_arrival, departure = r
        if next_arrival < labels[nb]:                    # строго меньше
            labels[nb] = next_arrival
            first[nb] = (nb, departure) if node == source else first[node]
            push(heap, (next_arrival, nb))
return None
```

Метка узла — **тик прибытия** пакета в него; пакет может ждать в узле сколько угодно (до дедлайна), ожидание бесплатное: следующий хоп берётся с `earliest = arrival` (в коде написано, docstring `ContactPlan`: «waiting closure on every edge … not Dijkstra on the current-neighbor graph»). Цель — самое раннее прибытие в назначение; число хопов само по себе не минимизируется. `first[node]` хранит **первый хоп** лучшего пути: как только назначение выходит из кучи, возвращается он.

**Правила ничьей** (вывод из чтения): из кучи выходит запись с меньшим `(тик, номер узла)`; метка меняется только при строгом улучшении, поэтому при равном прибытии побеждает путь, найденный раньше (узлы обходятся по возрастанию номеров); внутри ребра — лексикографический минимум `(прибытие, вылет)`.

## 5. Один хоп по ребру: `_edge_arrival`

Для ребра `{u, v}` перебираются его контакты по порядку (интервалы упорядочены и не пересекаются; конец контакта **не включается**). Для контакта: `start = max(earliest, начало контакта)`, `stop = min(конец контакта, deadline)`; если `start >= stop` — контакт пропускается. Пакет вылетает в тике `departure ∈ [start, stop − s_min]`, где `s_min` — длительность хопа при нулевой дальности (`service_ticks(size, rate, 0.0, c, tick_s)`, не меньше 1 тика). Длительность в вылет-тике: `service_ticks(..., distance_at(departure, u, v), ...)` — **расстояние на момент вылета**; прибытие `arrival = departure + duration`. Условие допустимости: `arrival <= stop` — **хоп должен целиком уместиться в один контакт** (и в срок); завершение ровно на границе конца контакта разрешено (комментарий `Contact`: «completion exactly at this boundary allowed»). Выбирается лексикографический минимум `(arrival, departure)` по всем контактам; поиск обрывается, когда ни один дальнейший вылет не может улучшить результат (`departure + s_min >= лучшее прибытие или limit`; комментарий кода приводит доказательство, что обрыв точный). `limit` — текущая метка соседа: принимаются только прибытия строго меньше неё.

Ручной расчёт при умолчаниях: `service_ticks` при размере 18000 байт и скорости 12500 байт/с даёт **15 тиков** для любой дальности от 0 до 3500 км (часть A, раздел 7); поэтому `s_min = 15`, и контакт короче 15 тиков хоп принять **не может** (диапазон вылетов `range(start, stop − 15 + 1)` пуст).

*Пример правил (ручной расчёт; тот же шаг по ребру, что в части D2, раздел 3 (a); `s_min = 15`, любой хоп занимает 15 тиков, дедлайн далеко).* Ребро {0,1}, контакт `[0,30)`, `earliest = 0`: `start = max(0, 0) = 0`, `stop = min(30, deadline) = 30`; вылеты `range(0, 30 − 15 + 1)`, то есть 0…15. Вылет 0: `arrival = 0 + 15 = 15 <= 30`, `best = (15, 0)`. Вылет 1: `1 + s_min = 16 >= 15` (лучшее прибытие) — обрыв, остальные вылеты не рассматриваются; результат `(15, 0)`. Ребро {1,2}, контакт `[20,60)`, `earliest = 15` (пакет прибыл в узел 1 в тике 15): `start = max(15, 20) = 20`, `stop = 60`; вылет 20, `arrival = 35`; результат `(35, 20)`: пакет ждёт в узле 1 с тика 15 до тика 20. Если бы контакт {0,1} был `[0,10)`: `stop = 10`, `range(0, 10 − 15 + 1)` пуст, результат `None`. Полный поиск по трём узлам — часть D2, раздел 3.

## 6. Что означает ответ и что делает симулятор

| Ответ | Смысл | Реакция `_schedule` |
|---|---|---|
| `Decision(v, t)` с `t == tick` | есть путь, первый хоп можно начать сейчас | если `v ∈ permitted` — старт; иначе `blocked_decision_calls`, ожидание, повтор в следующем тике |
| `Decision(v, t)` с `t > tick` | первый контакт начнётся позже | `last_wait = "scheduled_future_contact"`, ожидание; в тике `t` расчёт повторится (с новым `now`) |
| `None` | при вылетах не раньше `now` и прибытии не позже дедлайна пути нет (в коде написано, комментарий: «None means no feasible path with departures >= now») | ожидание; пакет опрашивается снова (или сразу отвечает память) |

Расчёт в тике `t` может дать другой первый хоп, чем в тике `t−1`: план одинаков, но `now` растёт, а ожидание в узлах бесплатно; вывод из чтения — устойчивость «того же» хопа нигде не гарантируется.

## 7. Отношение к реальности модели

План «знает» геометрию (положения спутников на всём горизонте) и **не знает** очередей, занятости узлов, буферов и случайных отказов передач. Поэтому CGR может назначить хоп, который в момент вылета не пройдёт проверку `permitted` (сосед занят, буфер полон) или сорвётся (`edge_tick_failure`). Продолжение — в части D2.
