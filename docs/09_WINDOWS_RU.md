## 3. Скачать zip с GitHub и распаковать

1. На странице репозитория GitHub нажмите «Code» → «Download ZIP» (по документации GitHub; не проверялось). Архив обычно содержит одну верхнюю папку вида `<имя репозитория>-<ветка>`, например `coursework_2-main` (вывод из общего опыта, не проверялось).
2. Распакуйте в КОРОТКИЙ путь без пробелов и кириллицы, не в OneDrive и не на рабочий стол (часто синхронизируется), например `C:\work\cw2`. Тогда корень проекта — `C:\work\cw2\coursework_2-main` (ниже — «папка проекта»). Причины (в коде написано, `run_all.py`, предупреждения и проверка длины пути): пути с OneDrive/Dropbox, пробелами или не-ASCII символами дают предупреждения; слишком длинный путь плана при выключенных длинных путях — ошибка. В «Распаковать всё» Проводника иногда получается лишний вложенный уровень папок: корнем считается та папка, где лежат `src`, `experiments`, `config.yaml` — проверьте командой `dir` (раздел 8).
3. НЕ переименовывайте и не переносите папку проекта после создания `.venv` и после стадии `plan`: план привязан к абсолютному пути (в коде написано в `docs/05`; ошибка «plan moved», раздел 13), а `.venv` хранит абсолютные пути (по документации Python `venv`).
4. Где взять SHA коммита для `config.yaml` (в коде написано, `REVISION_HELP` в `run_all.py`): на странице репозитория выберите ту ветку, которую скачали, нажмите «Commits» и скопируйте полный SHA верхнего (самого нового) коммита кнопкой копирования рядом с ним. Нужны ровно 40 символов: цифры и буквы a-f в нижнем регистре. Скрипт git не запускает и zip-файл не читает; он проверяет только вид строки (`[0-9a-f]{40}`), а не то, что SHA совпадает с вашей папкой. Если репозиторий изменился после скачивания, верхний коммит на сайте может не соответствовать вашей копии: это значение вы записываете как заявленную ревизию, проверить его код не может.

## 9. Настройка `config.yaml`

Файл читается как UTF-8 (допускается BOM; в коде написано: `read_text(encoding="utf-8-sig")`); комментарии на русском допустимы. Расширение должно быть `.yaml`, `.yml` или `.json` (иначе: «the config file name must end with .yaml, .yml or .json»). Для `.yaml` нужен PyYAML. Неизвестный ключ — ошибка (ловит опечатки). Обязателен только `revision`; остальные ключи и разделы можно опустить: подставятся значения по умолчанию из таблицы. Относительные пути ВНУТРИ конфигурации считаются от папки проекта; путь после `--config` и после `--output-root` — относительно текущего каталога cmd.

| Ключ | Тип, умолчание | Что значит и какую проверку делает `run_all.py` |
|---|---|---|
| `revision` | строка, обязателен; в файле заглушка, не SHA | Ровно 40 символов `[0-9a-f]`; идёт в `--revision` стадий plan, train, execute. В YAML — в двойных кавычках (без них длинное число может прочитаться как число; ошибка «revision must be a string»). |
| `suite` | строка, `configs/suite_m1b_cgr.json` | Файл набора; читается как UTF-8 JSON без BOM; рядом должны лежать `core_template` и `simulation_template`, названные в нём. → `plan --suite`. |
| `output_root` | строка, `outputs/run_001` | Папка результатов: `plan\`, `summary.json`, `plots\`, `run_all.log` (с `--debug`). Не внутри `src`, `.venv`, `configs`, `driver`, `docs`, `experiments`, `.vscode`; диск должен существовать. Папка `plan\` не должна существовать, поэтому для КАЖДОГО нового полного запуска нужен новый `output_root` (раздел 10, предупреждение). Переопределяется параметром командной строки `--output-root <путь>` (раздел 10.3). Держите путь коротким (пример из сообщения скрипта: `C:\w\r1`). |
| `stages` | список, все пять | Подмножество `plan, train, execute, aggregate, plot`; порядок всегда такой; повтор — ошибка; перекрывается ключом `--stages a,b`. Если `plan` не в списке, `plan.json` должен уже существовать. |
| `plan.models` | строка или `null` | JSON-файл «N → папка готового обучения»; → `plan --models`. Файл должен существовать. |
| `plan.baselines_only` | `false` | `true` — GLR не планируется (остаются TBR, TSR, CGR); стадия `train` пропускается с сообщением `NOTICE`; `execute` не требует `torch_geometric`. |

| `plan.tbr_max_nodes`, `plan.tbr_max_expansions` | целое > 0 или `null` | Только вместе с `include_native_tbr: true`. |
| `aggregate.allow_partial` | `false` | Разрешает итог по неполному набору ячеек. |
| `aggregate.reference` | `TBR_style_hop_oracle` | Одно из: `GLR`, `TBR_style_hop_oracle`, `TSR_source_dijkstra`, `CGR_contact_plan`, `TBR_bounded_exhaustive_reference` (последнее — только с `include_native_tbr`; `GLR` — не с `baselines_only`). |

| `run.progress_interval_s` | число ≥ 0, `60` | Период строки `[heartbeat]` в секундах; `0` отключает. |

Подводные камни (по документации YAML и cmd; не проверялось): в YAML внутри двойных кавычек обратная косая черта — начало escape-последовательности, поэтому `output_root: "C:\work\r1"` ошибочно; пишите `C:/work/r1` или без кавычек `C:\w\r1`. ## 10. Запуск

Все команды — из папки проекта, `.venv` включён. Форма с обратной косой чертой и форма с прямой (как в запросе) равнозначны для Python (по документации; не проверялось).

**ВАЖНО: два полных запуска подряд с одним `config.yaml` не получатся.** `--debug` не сокращает прогон (раздел 10.2): `--debug` и обычный запуск — это по одному ПОЛНОМУ прогону каждый. Первый прогон создаёт `<output_root>\plan\` (а затем `summary.json` и `plots\`); код отказывается использовать существующий вывод, а скрипт ничего не удаляет (в коде написано: проверка в `preflight_inputs`). Поэтому второй запуск с тем же `output_root` остановится сразу, с «PRE-FLIGHT PROBLEM: plan folder already exists: ...», «Nothing was started.» и кодом 3. Перед вторым полным запуском смените `output_root` в `config.yaml` (например, `outputs/run_002`), или задайте другую папку параметром `--output-root` (например, `--output-root outputs\run_002`; раздел 10.3), или удалите прежнюю папку вывода вручную (10.6). Сухой прогон (`--dry-run`) ничего не создаёт и повторяется сколько угодно. Если полный прогон нужен один раз, достаточно варианта с `--debug`: он делает то же, что обычный, и дополнительно пишет `run_all.log` и пробные проверки. Это вывод из чтения кода; не проверялось.

### 10.1. Сухой прогон (ничего не запускает и не создаёт)

```
REM НЕ ЗАПУСКАЛОСЬ.
python experiments\run_all.py --config config.yaml --dry-run
echo %ERRORLEVEL%
```

В коде написано: проверяются конфигурация, файлы, присутствие пакетов (поиском без импорта; отсутствующий пакет — ошибка и в сухом прогоне), каждая команда стадии проверяется настоящим разбором аргументов `ssn_hops.experiments`; затем печатаются команды ровно в том виде, в каком они были бы запущены. Ожидаемые строки в конце (текст из кода): «Pre-flight checks passed (by inspection of files and package presence only).», список «Commands in order (N):», «Nothing was executed. No file or folder was created.»; код возврата 0. Стадии, их аргументы (как строит `stage_args`): `plan --suite <набор> --out <output_root>\plan --revision <SHA>` [`--models`, `--baselines-only`, `--include-native-tbr`, `--tbr-max-nodes`, `--tbr-max-expansions`]; `train --plan <output_root>\plan\plan.json --revision <SHA>`; `execute` — те же аргументы; `aggregate --plan ... --out <output_root>\summary.json` [`--allow-partial`] `--reference <имя>`; `plot --summary <output_root>\summary.json --out <output_root>\plots` [`--allow-partial`]. Каждая команда начинается с `<python.exe> -m ssn_hops.experiments`.

Строка «No file or folder was created.» относится к процессу самой обёртки `run_all.py`: стадии в сухом прогоне не запускаются, а перед импортом пакета `ssn_hops` (для проверки аргументов настоящим разбором) скрипт устанавливает `sys.dont_write_bytecode = True`, чтобы не оставлять файлы `.pyc` в `src\ssn_hops` (в коде написано; запуском не проверялось).

**Пробный `plan` в отдельной папке (шаг между сухим прогоном и долгим запуском).**

```
REM НЕ ЗАПУСКАЛОСЬ. Одна стадия plan, без torch; пишет файлы только внутри outputs\scratch.
python experiments\run_all.py --config config.yaml --stages plan --output-root outputs\scratch
echo %ERRORLEVEL%
```

- В коде написано: `--stages plan` заменяет список стадий из конфигурации; для одной стадии `plan` функция `required_modules` возвращает пустой список, то есть предполётная проверка не требует ни `torch`, ни `numpy` (они нужны для `train`/`execute`, `matplotlib` — для `plot`). Сама команда `plan` по docstring функции `make_plan` не импортирует `torch` и симулятор.
- Что создаётся (в коде написано, `make_plan`): только папка `outputs\scratch\plan` с файлами конфигураций и `plan.json`; недостающие родительские папки (`outputs`, `outputs\scratch`) создаются при этом тоже (`mkdir(parents=True)`). Файлов `summary.json` и папки `plots` нет. Относительный путь после `--output-root` считается от текущего каталога cmd: запускайте из папки проекта. Удалить результат можно вручную (команда `rmdir /s /q`, предупреждение в 10.6: это ваша команда, а не скрипта).
- Ожидание, не наблюдение: код возврата 0; время порядка секунд (вывод из чтения: стадия только разбирает конфигурации и пишет небольшие файлы; не измерялось); в конце вывода стадии JSON с ключами `plan`, `sha256`, `mode`, `models_required`, `scenarios` и `runs` (так возвращает `make_plan`; значения не известны, не наблюдались).
- Что этот шаг не проверяет: установку и загрузку `torch`/`torch_geometric`, стадии `train`, `execute`, `aggregate`, `plot`. Папка `outputs\scratch` долгим запуском не используется: `config.yaml` не меняется, настоящий `output_root` остаётся прежним (по умолчанию `outputs/run_001`).
- Если шаг не удался, пришлите данные по разделу 12.

### 10.2. Запуск с `--debug`

```
REM НЕ ЗАПУСКАЛОСЬ. Запускает ВСЕ стадии конфигурации: тяжело.
python experiments\run_all.py --config config.yaml --debug
```

Что `--debug` делает В РЕАЛИЗАЦИИ (`run_all.py`):
1. Печатает блок «--- debug report ---»: версия и реализация Python, платформа, `sys.executable`, предпочитаемая кодировка и флаг `utf8_mode`, папка проекта, `output_root`, длина пути папки плана, значение `LongPathsEnabled` из реестра Windows (чтение; «unknown or not Windows», если не удалось), переменные окружения, которые скрипт задаёт стадиям (не весь `environ`).
2. Задаёт стадиям дополнительно `PYTHONFAULTHANDLER=1` (остальное — `PYTHONPATH=<папка проекта>\src` [+ прежний `PYTHONPATH`], `PYTHONUTF8=1`, `PYTHONIOENCODING=utf-8`, `PYTHONUNBUFFERED=1` — задаётся всегда).
3. После успешной предполётной проверки открывает `<output_root>\run_all.log` (дозапись, UTF-8; создаёт папку `output_root`), записывает в него всё напечатанное ранее и дублирует весь дальнейший вывод. В лог не попадает ничего, если предполётная проверка не прошла.
4. Печатает команды и дополнительно списком `argv` (`repr`).
5. До стадий запускает до двух пробных процессов (их stdout и stderr показываются). Первый — проверка реального импорта пакетов, нужных запрошенным стадиям (`python -c "import ...; print('imports ok: ...')"`); его же без `--debug` запускает флаг `--check-imports`. Второй — `python -m ssn_hops environment`, если запрошена стадия `train` или `execute` без `baselines_only` (только с `--debug`). Провал пробы — код 3.
6. Печать последних 40 строк `stderr` упавшего задания (раздел 10.5) выполняется В ЛЮБОМ режиме, не только с `--debug` (справка `--help` этого `--debug` больше не приписывает; поведение — по коду).

Чего `--debug` НЕ делает: не сокращает прогон (в экспорте нет малого набора; стадии и ячейки те же), не включает трассировки Python (необработанная ошибка самого скрипта печатает трассировку в любом режиме, код 1), не ограничивает время. `--debug` можно сочетать с `--dry-run`: тогда будут блок отчёта и команды списком `argv`, лог не создаётся.

### 10.3. Обычный запуск

```
REM НЕ ЗАПУСКАЛОСЬ. Запускает ВСЕ стадии конфигурации: тяжело. Нужен новый output_root, если прежний уже использован (см. предупреждение выше).
python experiments\run_all.py --config config.yaml
```

Для каждой стадии (в коде написано) печатаются «=== stage <имя>: start ===», строка `command: ...`, построчно вывод стадии, затем «=== stage <имя>: exit code N after HH:MM:SS ===»; при первой неудаче остановка. Что делает каждая стадия: `plan` — записывает план (конфигурации и команды), ничего не обучает и не считает; `train` — обучает модели GLR (тяжёлая стадия; `torch`, `torch_geometric`); `execute` — выполняет все ячейки; `aggregate` — собирает `summary.json`; `plot` — строит графики (`matplotlib`). Подробности стадий — `docs/05_EXPERIMENTS_RU.md`. Только часть стадий: `--stages plan,aggregate` и т. п. (порядок фиксирован; предполётная проверка требует, чтобы вход предыдущих стадий уже существовал).

Параметр `--output-root <путь>` (в коде написано; текст справки: «folder for plan/, summary.json, plots/ and run_all.log; overrides the config key output_root; a relative path is taken relative to the current directory (like --config)»): заменяет ключ `output_root` на время этого запуска, файл конфигурации не меняется. Путь приводится к абсолютному от текущего каталога cmd; пустое значение — «CONFIG ERROR: --output-root must be a non-empty string». Строка «output folder: ...» в начале вывода показывает действующую папку; все проверки (запрет внутри `src`, `.venv`, `configs`, `driver`, `docs`, `experiments`, `.vscode`, длина пути, существующий `plan\`) применяются к ней. Пример второго полного запуска с другой папкой: `python experiments\run_all.py --config config.yaml --output-root outputs\run_002`.

### 10.4. Ход работы и `[heartbeat]`

Стадии `train` и `execute` по чтению печатают только итоговую строку JSON, поэтому долгая тишина ожидаема. Пока идёт стадия `train` или `execute`, скрипт раз в `run.progress_interval_s` секунд печатает строку вида «[heartbeat] execute: K of T jobs have a status file (failed ones included), elapsed HH:MM:SS». В коде написано: `K` — число файлов `*.status.json` в `<output_root>\plan\logs` (считаются по именам, содержимое не читается; для `execute` — имена, начинающиеся с `s-`, для `train` — остальные: это допущение скрипта об именах, вывод из чтения), `T` — число заданий по `plan.json` или `?`, если прочитать не удалось. Строка показывает, что процесс жив и сколько заданий завершилось, а не удачно ли.

### 10.6. Прерывание (Ctrl+C)

В коде написано: при Ctrl+C скрипт печатает «Interrupt received: waiting up to 10 s for the stage to stop (press Ctrl+C again to end it now)»; консоль Windows доставляет сигнал всей группе процессов (по документации), поэтому дочерний процесс тоже получает его. Если стадия не остановилась за 10 с (или нажат второй Ctrl+C), скрипт завершает дерево процессов стадии командой `taskkill /PID <pid> /T /F` (встроенная утилита Windows; затрагивает только это дерево), при неудаче — `proc.kill()`. Результат стадии неполный; возобновления нет (у `train`, `execute`, `aggregate`, `plot` нет кода продолжения: вывод из чтения; они отказывают, если вывод уже есть). Чтобы начать заново: выберите другой `output_root` ИЛИ удалите папку вывода вручную. Команда `rmdir /s /q <путь>` УДАЛЯЕТ папку со всем содержимым без корзины; это ваша команда, а не скрипта (он ничего не удаляет); проверьте путь дважды. Закрытие окна cmd или VS Code во время прогона может оставить дочерние процессы или оборвать их: не установлено; перед перезапуском посмотрите в Диспетчере задач процессы `python.exe` (по документации Windows; вывод из чтения).

## 11. Долгий прогон: альтернатива в WSL2

Нативный путь не даёт ни лимитов времени ячейки, ни срезов, ни возобновления: драйвер (`driver/run_cell`, `driver/train_unit`) в Windows не работает (раздел 14). Если нужны лимиты, срезы и возобновление, долгий прогон выполняется драйвером в WSL2 (Linux в Windows) по `docs/08_VSCODE_SETUP_RU.md` (проект внутри файловой системы Linux, не в `/mnt/c`). Это отдельный путь: `run_all.py` в нём не используется. Какой путь быстрее или надёжнее на вашем ПК, не установлено.

## 12. Что прислать при сбое

Уберите секреты и личные данные (токены, пароли, адреса электронной почты). Первый запуск — первая проверка, поэтому присылайте по возможности всё:
1. Точную команду и текущий каталог (`cd`).
2. ВЕСЬ вывод с первой строки (stdout и stderr), например из окна cmd целиком или `... > out.txt 2>&1` (по документации cmd; перенаправление записывает файл в текущий каталог).
3. Код возврата: `echo %ERRORLEVEL%` сразу после команды.
4. `python --version` и `pip list`.
5. Сведения об ОС: `systeminfo` — строки «Название ОС» / «OS Name» и «Версия ОС» / «OS Version».
6. Листинг папки вывода: `dir /s /b <output_root>` (по документации cmd); для сбоя задания — файлы `<output_root>\plan\logs\*.stderr.txt` и `*.status.json` упавшего задания.
7. `<output_root>\run_all.log` (есть только если запуск шёл с `--debug`).
8. Если сбой при установке: полный вывод `pip install ...`.

| `ValueError: source files changed since planning; create a new plan` | после записи плана изменён, добавлен или удалён файл `*.py` в `src\ssn_hops`: код сравнивает хеши SHA-256 всех `*.py` этой папки с записанными в плане (в коде написано: `experiment_io.execution_guard` и `source_hashes`; в `experiments` их вызывают стадии `train` и `execute`); гипотеза о причине: файл пересохранён редактором (например, другие концы строк или BOM) или изменён намеренно | не править `src`; редактируемая установка (раздел 7); иначе новый `output_root` и новый план |
| `source hash mismatch ...` (это текст драйвера: «refused: source hash mismatch: the installed ssn_hops bytes differ from the planned bytes in ...»; текст стадий `train` и `execute` из `experiments` — в строке выше) | изменён или пересохранён файл `src\ssn_hops\*.py` после плана, либо в разных стадиях импортируются две копии пакета | не править `src`; редактируемая установка (раздел 7); иначе новый план |
| `FileExistsError: ... plan output must be a new directory` или `FileExistsError` на `...started.json`/`execution_started.json` | вывод уже есть (прежний, возможно оборванный запуск; вывод из чтения) | другой `output_root` |
| `UnicodeDecodeError` или «кракозябры» (например, `РїСѓС‚СЊ`) в тексте логов | скрипт читает вывод стадий как UTF-8 с заменой ошибок и задаёт `PYTHONUTF8=1`, `PYTHONIOENCODING=utf-8` (в коде написано); гипотеза: файл открыт программой, считающей его cp1251, или стадия запущена вручную без этих переменных | открывать логи в VS Code (UTF-8); вручную задать переменные (`set PYTHONUTF8=1`) |
| `STAGE FAILED: <стадия> exited with code N` | стадия вернула не 0; причина — в хвосте `stderr` ниже | прислать всё (раздел 12) |
| `"python" не является внутренней или внешней командой...` / `'python' is not recognized as an internal or external command` | Python не в PATH (текст cmd; по документации) | использовать `py`, переустановить с «Add python.exe to PATH» |
| `ModuleNotFoundError: No module named 'ssn_hops'` при ручной команде `python -m ssn_hops...` | нет редактируемой установки и `PYTHONPATH` (`run_all.py` задаёт его стадиям сам) | `pip install -e ".[plot,yaml]"` или `set PYTHONPATH=%CD%\src` |
| PowerShell: «running scripts is disabled on this system» при `Activate.ps1` | политика выполнения скриптов (по документации) | использовать cmd и `activate.bat` (раздел 6) |

## 14. Что на Windows не поддерживается

- Драйвер: `driver/run_cell.py` и `driver/train_unit.py` при `os.name != "posix"` бросают `OSError("capped runs need POSIX process groups (Linux/WSL2); Windows-native is out of scope")` (в коде написано; цитата по `docs/08`). Остальные модули драйвера (`selector`, `finish`, `ledger`, `traces`) на Windows не проверялись; `finish.py` и `traces.py` по чтению используют жёсткие ссылки `os.link`. Лимиты ячеек и обучающих единиц, срезы, журнал и возобновление доступны только через драйвер в WSL2 (`docs/08`).
- Конфигурации `c)`-`g)` в `.vscode/launch.json` помечены `[POSIX/WSL2 only]`; `a)`, `b)`, `h)`, `i)` вызывают команды конвейера (вывод из чтения: платформенно нейтральны).
- Значения хешей и байты файлов JSON, записанные на Windows, отличаются от записанных в Linux (запись текста превращает конец строки в CRLF; вывод из чтения): хеши разных ОС не сравнивайте. Не открывайте и не пересохраняйте файлы папки вывода в редакторах (BOM или смена концов строк портят проверку).

## 15. Что не установлено

- Что скрипт `run_all.py` вообще запускается и что его проверки верны: он не запускался никем.
- Что `pip` ставит `torch`, `torch-geometric`, `numpy`, `matplotlib`, `PyYAML` на вашем ПК и что `torch` загружается (DLL); совместимость конкретных версий.
- Поведение антивируса, OneDrive, индексатора; замена файла `best.pt` под блокировкой.
- Время и объём диска; число часов, которое займёт `execute`; число процессов и память.
- Поведение VS Code (настройки терминала, выбор интерпретатора, отладчик); поведение `taskkill` и Ctrl+C в вашей консоли; что происходит при сне ПК.
- Точные тексты ошибок Windows, `pip`, Python и PyTorch на вашей системе (графа «Текст» таблицы раздела 13 для них — по документации).
- Совпадение чисел с прежним прогоном в Linux: не обещается.
- Метки задач и ревизий, SHA коммитов и сведения о ветках — вне этой папки: проверять их по странице репозитория вам.
