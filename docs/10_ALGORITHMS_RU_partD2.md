## 1. Как строится план: `build_geometric_plan` (`contacts.py`)

В коде написано (docstring): «Stream graphs into intervals; retain positions only, never an H*N*N cube». Для каждого тика `tick = 0 … horizon_tick − 1`: положения спутников `trajectory.positions_km(tick · tick_s)`, граф `graph_from_positions` (тот же, что строит симулятор для снимка этого тика), множество рёбер `u < v`. Ребро, которого не было и которое появилось, открывает контакт; пропавшее — закрывает с `end_tick = tick` (конец **не включается**); открытые на последнем тике закрываются в `horizon_tick`. Результат — `ContactPlan(N, horizon_tick, intervals, distance_at)`, где `distance_at(tick, u, v)` — расстояние по сохранённым положениям. Смысл (строка `metadata()["semantics"]`): выборка в тике `k` действует на `[k·dt, (k+1)·dt)`.

Вывод из чтения: план и снимки симулятора согласованы только потому, что оба используют `positions_km(tick·tick_s)` и `graph_from_positions` (общего объекта нет: `GeometryNetwork` строит снимки, `build_geometric_plan` — свой цикл). План покрывает тики `[0, horizon_tick)`; дальше горизонта CGR не планирует (`deadline = min(expiry, horizon)`).

`ContactPlan.neighbors[u]` — все узлы, с которыми `u` **хоть раз** имел контакт за горизонт (по возрастанию), а не текущие соседи.

## 2. Память отрицательных ответов `_none_memo`

В коде написано (комментарий): ответ `None` в тике `t` означает `None` во всех тиках `t' >= t` для того же `(location, destination, expiry_tick, size_bytes)`, потому что любой путь, допустимый с позднего тика, допустим и с раннего. Хранится `id(packet) → [packet, cfg, plan, {ключ: первый тик с None}]`. Запись сбрасывается, если пакет, `cfg` или `plan` — другие объекты. Вытеснения нет, запись держит ссылку на пакет: вывод из чтения — запись создаётся для каждого пакета, который хоть раз дошёл до `choose` (до поиска), поэтому внешний словарь растёт на одну запись на каждый такой пакет; внутренний словарь получает ключ только после ответа `None`. Положительные ответы не переиспользуются.

## 3. Пример «ручной расчёт»: три узла

Рёбра {0,1} и {1,2}; источник 0, назначение 2; пакет 18000 байт, умолчания, `s_min = 15`, дальности такие, что любой хоп занимает 15 тиков; дедлайн далеко.

*(a) Контакты {0,1}: `[0,30)`; {1,2}: `[20,60)`; `now = 0`.* Ребро {0,1}: `start = 0`, `stop = 30`, вылеты `0…15`; вылет 0 даёт прибытие 15; вылет 1 даёт `1 + 15 = 16 >= 15` — обрыв. Метка узла 1 = 15, `first[1] = (1, 0)`. Из узла 1: ребро {1,0} отклоняется (`limit = 0`, обрыв сразу); ребро {1,2}: `start = max(15, 20) = 20`, вылет 20, прибытие 35; метка узла 2 = 35, `first[2] = first[1]`. Назначение вышло из кучи: `PlannedHop(1, 0, 35)`, ответ `Decision(1, 0)` — идти в узел 1 немедленно. После хопа в узле 1 (тик 15) расчёт даст `Decision(2, 20)`: пакет ждёт 15…19 (`scheduled_future_contact`) и стартует в тике 20, если узел 2 допустим.

*(b) Контакт {0,1} начинается в тике 5: `[5,30)`.* Вылет 5, прибытие 20; на узле 1 `start = max(20, 20) = 20`, прибытие 35. Ответ `Decision(1, 5)`: при `now = 0` симулятор ждёт (`not_before_tick 5 > 0`), тики 0…4 — ожидание, расчёт повторяется каждый тик; в тике 5 снова `Decision(1, 5)`, теперь `not_before_tick == tick`: если узел 1 в `permitted` — старт, иначе `blocked_decision_calls` и повтор.

*(c) Контакт {0,1} короткий: `[0,10)`.* Вылеты `range(0, 10 − 15 + 1)` — пусто. Узел 1 недостижим, `earliest_hop` возвращает `None`, в память записывается `memo[key] = 0`; в тиках `>= 0` для того же ключа ответ `None` выдаётся без поиска (`plan_queries` при этом растёт).

## 4. Стоимость (вывод из чтения; времена не приводятся)

**Один вызов** `earliest_hop`: из кучи выходит не более `N` узлов; для каждого перебираются его `neighbors` (все бывшие смежными за горизонт; их число **не установлено**), и для каждого ребра `_edge_arrival` проходит его контакты и вылеты до первого, который нельзя улучшить; в каждом рассмотренном вылете — `distance_at` (норма разности двух 3-векторов) и `service_ticks`. При умолчаниях первый допустимый вылет контакта обрывает перебор (все хопы по 15 тиков). Худший случай на ребро — суммарная длина контактов ребра в тиках. Память вызова — `O(N)`.

**Построение плана** (раз на ячейку CGR): цикл по `horizon_tick` тикам, на каждом граф `N×N`: число проверяемых пар за построение `H·N²`; ручной расчёт при `H = 9000`: `N = 132` → 156 816 000, `N = 396` → 1 411 344 000 пар (это счёт пар, не время). Память: массив положений `H×N×3` float64 хранится всё время жизни плана (замыкание `distance_at`): `9000·132·3·8 = 28 512 000` байт ≈ 28,5 МБ при `N = 132` и `9000·396·3·8 = 85 536 000` байт ≈ 85,5 МБ при `N = 396` (ручной расчёт); плюс временный граф `N×N`. Число контактов `O(интервалы)`. План строится в `simulate.run_single` при каждом вызове для CGR (в коде написано: `build_geometric_plan(cfg)` в ветке `CGR_contact_plan`, время — в `timing.contact_plan_build_seconds`); как набор опытов вызывает `run_single` — не читалось. В ревизии 5 CGR входит в каждую ячейку набора, включая `N = 396` (по описанию ревизии; файлы набора при подготовке не читались): значит, план строится столько раз, сколько ячеек CGR.

Рост с `N` (вывод): время построения плана растёт как `N²` на тик; память положений — линейно по `N`; число вызовов `choose` — не больше `N` за тик (часть A).

## 5. Крайние случаи

- Назначение недостижимо по плану до дедлайна → `None`, пакет ждёт до TTL (память делает повторные вызовы дешёвыми).
- `now >= deadline` (пакет у границы TTL или горизонта) → `None`.
- План не прогнозирует очереди: назначенный хоп может не пройти `permitted` в тике вылета; тогда ожидание и новый расчёт.
- Случайный отказ (`edge_tick_failure`) план не прогнозирует; после срыва повтор по общим правилам (часть A, раздел 7).
- Топология между вызовами: план статичен, геометрия в нём уже содержит будущие изменения; предсказываются только они.
- Ошибки: узлы вне диапазона, `cfg.orbit.n != N` — `ValueError`.

## 6. Отношение к статье

Установлено чтением: в [11] CGR — Дейкстра по **плану контактов** на каждом промежуточном узле; [11] противопоставляет «temporal graph» (снимки) и план контактов; формального описания контактного графа в [11] нет (не установлено как структура); CGR, по [11], проигрывает по задержке потому, что узел должен ждать начала контакта. В открытом коде LSNS (`CGR.java`, чтение фрагментами): контактный граф с шагом 0,1 с, окно будущих контактов `[t, t + msgTtl]`, стоимость — прибытие плюс время ожидания контакта, при отсутствии звена пересчёт до 5 раз, один узел — одно звено. Наша реализация — независимая реконструкция, **не код статьи**: план строится из той же геометрической модели, что и симулятор; поиск — зависящий от времени Дейкстра с ожиданием; план спрашивается на каждом вызове, **кроме** запомненного `None` для того же `(location, destination, expiry_tick, size_bytes)` — он переиспользуется на последующих тиках, положительные ответы не запоминаются; счётчика пересчётов нет. Совпадение в принципе (Дейкстра по плану на каждом узле), детали (окно, лимит пересчётов, шаг плана) **не сопоставимы** и не установлены для версии кода авторов. Единица времени, TTL и параметры таблицы II [11] не установлены.
