## 1. simulator.py

### 1.1 Назначение
Докстринг: «Tick-quantized single-copy store-and-forward simulation (unexecuted here).» Заданный трафик проигрывается на сети, граф которой меняется по тикам. Единственная копия пакета лежит в очереди узла и передаётся по одному ребру за раз; время — целые тики (`cfg.tick_s`); следующий хоп выбирает политика (`policies.py`, часть A3).

### 1.2 Входы и выходы
- `Simulator(cfg, records, policy, network=None, failure_sampler=edge_tick_failure)`; `simulate(...)` с теми же аргументами равна `Simulator(...).run()`.
- `cfg` — `SimulationConfig` (в `__init__` вызывается `cfg.validate()`). `records` — `TrafficRecord`; `traffic.validate_records` проверяет их и сортирует по `(created_tick, packet_id)` (`ValueError`). `policy` — объект с `name`, `choose(packet, context)`, `stats()` (утиная типизация). `network` — объект с `snapshot(tick)` → `(adjacency, ranges)` и необязательным `snapshot_builds`; при `None` строится `GeometryNetwork(cfg)`. `failure_sampler(seed, u, v, tick, probability)` → `bool`.
- Выход `run()` — словарь `{"summary", "packets", "events"}` (часть A2). Файлов не пишет.

### 1.3 Основные классы и функции

#### 1.3.1 Объекты и состояние
`Packet` (изменяемый dataclass): `packet_id, created_tick, source, destination, size_bytes, expiry_tick, location`, `status="scheduled"`, `admitted=False`, `terminal_tick=None`, `terminal_reason=None`, `queued_tick=0`, `visited=set()`, `hops=0`, `hop_failures=0`, `total_aborts=0`, `header=None` (список узлов; его заполняет TSR), `last_wait=None` (диагностическая строка). В `__init__`: `expiry_tick = created_tick + cfg.ttl_ticks`, `location = source`, `queued_tick = created_tick`, `visited = {source}`. Статусы: `scheduled` (не принят), `pending` (хранится в очереди узла `location`, в том числе пока с него идёт передача), `in_transition` (только внутри `_complete`), `delivered`, `failed`. `Transfer` (frozen): `packet_id, sender, receiver, start_tick, finish_tick`.

Состояние `Simulator`: `queues[node]` — список `packet_id`; `used[node]` — байты пакетов в очереди; `reserved[node]` — байты под входящие передачи; `busy` — узлы, занятые передачей (и отправитель, и получатель); `active` — `packet_id → Transfer`; `events`; `terminal_ids`; `counts` (`Counter`, 11 ключей с нуля): `admitted, injection_rejected, route_calls, route_wait_calls, future_contact_wait_calls, blocked_decision_calls, started_transfers, aborted_transfers, cancelled_transfers, completed_hops, completed_hop_bytes`; `abort_reasons` (`Counter`); `route_seconds`, `topology_seconds` (0.0); `tick`; `_ran`. `event(kind, packet, **details)` добавляет `{"tick", "time_s" = tick * tick_s, "kind", "packet_id", **details}`; виды: `generated, admitted, transfer_started, transfer_aborted, transfer_cancelled, hop_completed, terminal`. Для собственной сети хранится `_own_network`; константа модуля `_SELF_BUILT_NETWORK_TYPE = GeometryNetwork` связана при импорте.

Дисциплина очереди (комментарий в `_schedule`: «Strict local-receive FIFO: only a node's head may attempt to send.»): очередь — порядок приёма, отправиться пытается только голова `queues[node][0]`. Вывод из чтения: если для головы политика отвечает ожиданием, пакеты за ней не рассматриваются (блокировка головы) до её отправки или терминального исхода.

Буфер: ёмкость узла — `cfg.buffer_bytes` (по умолчанию `16000000`, `sim_config.SimulationConfig`). Пакет в передаче остаётся в `queues` и `used` отправителя до завершения хопа; получатель резервирует `size_bytes` в `reserved` при старте. Инвариант `0 <= used + reserved <= buffer_bytes` проверяет `audit`. Ручной расчёт: `16000000 / 18000 ≈ 888.9` — по умолчанию в узле помещается не более 888 пакетов полного размера.

#### 1.3.2 Элементарные операции
- `_release_transfer(packet)`: удаляет передачу из `active`, отправителя и получателя — из `busy` (`set.remove`: при рассогласовании `KeyError`), `reserved[receiver] -= size_bytes`; возвращает `Transfer`.
- `_remove_stored(packet)`: убирает `packet_id` из `queues[location]`, `used[location] -= size_bytes`.
- `_terminal(packet, status, reason)`: уже терминальный пакет → `RuntimeError("duplicate packet terminal transition")`. Активную передачу снимает (`_release_transfer`, `cancelled_transfers += 1`, событие `transfer_cancelled`); при `status == "pending"` вызывает `_remove_stored`; задаёт `status`, `terminal_tick = tick`, `terminal_reason`, `last_wait = None`; добавляет в `terminal_ids`; событие `terminal`. Вывод из чтения: отмена активной передачи здесь возможна только по TTL (часть A2, шаг 4 тика).
- `_complete(packet)`: `_release_transfer`; `_remove_stored` (у отправителя); `location = receiver`; `hops += 1`; `hop_failures = 0`; `visited.add(location)`; `completed_hops += 1`; `completed_hop_bytes += size_bytes`; событие `hop_completed`. Затем `status = "in_transition"` (комментарий: терминал не должен удалять вторую копию у отправителя) и: `location == destination` → `_terminal("delivered", "delivered")`; иначе `hops >= 2 * cfg.orbit.n` → `_terminal("failed", "hop_limit")`; иначе `status = "pending"`, `queued_tick = tick`, `last_wait = None`, `packet_id` — в хвост `queues[location]`, `used[location] += size_bytes`. Доставка проверяется раньше лимита хопов. Ручной расчёт: `orbit.n = 132` (`config.OrbitConfig.n`) → лимит `2 * 132 = 264` хопа; это не поле конфигурации.
- `_inject(packet)`: событие `generated`. Если `size_bytes > buffer_bytes` — `injection_rejected += 1`, терминал `failed/packet_oversize`. Иначе если `used[source] + reserved[source] + size_bytes > buffer_bytes` — `injection_rejected += 1`, терминал `failed/injection_buffer`. Иначе `status = "pending"`, `admitted = True`, `admitted += 1`, хвост `queues[source]`, `used[source] += size_bytes`, событие `admitted`. Вывод: переполненный буфер источника в момент создания — немедленный отказ, ожидания нет.

#### 1.3.3 Единый путь отмены передачи и правило повторов
В коде написано (`simulator.py`, `Simulator._abort`; вызовы — в `Simulator.run`, шаг 5 тика, часть A2): обе причины отмены — `link_loss` (`adjacency[sender, receiver]` ложно на текущем тике) и `edge_tick_failure` (`failure_sampler` вернул истину) — вызывают один и тот же метод `self._abort(packet, reason)`. Он: `_release_transfer`; `packet.hop_failures += 1`; `packet.total_aborts += 1`; `aborted_transfers += 1`; `abort_reasons[reason] += 1`; событие `transfer_aborted(sender, receiver, reason, hop_failed_attempts)`; если `hop_failures > cfg.additional_retries` — `_terminal("failed", "retry_exhaustion")`. Причина влияет только на строку `reason` (счётчик `abort_reasons` и событие); счётчик `hop_failures` и порог `additional_retries` общие для обеих причин. Иначе пакет остаётся в очереди отправителя; комментарий: «the same sender copy can restart, from byte zero, this tick».

Ручной расчёт при `additional_retries = 3` (`sim_config.SimulationConfig`): отмены №1–№3 дают `hop_failures = 1, 2, 3` (`> 3` ложно), отмена №4 даёт `4 > 3` и `retry_exhaustion`. Вывод из чтения: `hop_failures` относится к пакету на текущем хопе, а не к ребру: сбрасывается только в `_complete`, смена получателя при повторе его не сбрасывает; `total_aborts` не сбрасывается никогда.
